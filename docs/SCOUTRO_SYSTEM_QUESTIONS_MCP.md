# Structured system questions and the agent MCP adapter

`POST /v1/chat/completions` detects supported German/English system questions before model selection, attachments, RAG, web search or tool calling. Examples: “Wie viele Hosts sind im System?”, “Wie viele Seiten?”, “Welche Crawls laufen?”, “Ist Discovery aktiv?”, “Welche Collections gibt es?” and “Analysiere Host example.test”. Content questions retain the existing chat path. The `/system` prefix forces system routing (for example `/system Wie viele Seiten?`). Unsupported quantitative host/page questions and questions mentioning `im System`/`in Scoutro`/`in the system` fail clearly. This is a deterministic DE/EN router, not unrestricted semantic intent recognition; unsupported phrasing should use the structured endpoints or an explicit `/system` question. Only the latest user text is routed; indexed page text, attachments and LLM-provided tool choices never supply system facts.

System answers render a readable summary of the authorized action result, retaining the full structured facts in response metadata. They work without a configured model or Function Calling. The response uses OpenAI chat completion JSON or SSE (`stream=true`, terminal `[DONE]`), with `scoutro.kind`, `action`, `observedAt`, `facts` and `answer`. It does not create citations or change Citation processing. Missing permissions/data return a structured error, not an estimate or substitute search. The chat UI displays API error messages and a translated authentication explanation.

## Authentication and scope

Chat system data requires the container administrator role (HTTP Digest), or `Authorization: Bearer` for an active Scoutro agent token. There is no localhost/admin bypass. Existing AIShield and chat rate limits still apply; agent calls also go through AgentApi authorization, rate limiting and audit. Tokens never become administrator credentials.

`GET /scoutro/api/v1/system/questions?q=...` is administrator-only. `GET /scoutro/api/agent/v1/system/questions?q=...` delegates to the exact selected action; there is no broad `system.questions` grant. The endpoint accepts only `q` (up to 1000 characters) and optional `collection`. Chat accepts `collection` in the JSON body. Index and SEO reads intersect the selected collection with the server-resolved agent scope. Collection lists retain the agent's granted collections; crawl lists retain existing ownership restrictions. Discovery status is global metadata and still requires explicit `discovery.status`, available only to external agents and absent from presets. Collection selection does not turn global Discovery metadata into scoped data.

`GET .../index/metrics` requires administrator authentication or explicit agent `index.metrics`. It accepts only `collection`; raw Solr syntax is rejected. It returns `documents` (all indexed records), `pages` (HTTP 200 without failtype), `hosts` (distinct successful `host_s`), server-resolved `collections` (`null` means explicitly unrestricted), `definition` and `observedAt`. Hosts are not registrable domains. One bounded JSON-facet request on the configured local core (`distrib=false`, no shard estimate) deduplicates records and hosts across overlapping collections; partial, unsupported or failed aggregates and missing HTTP-status/host metadata needed for complete counts return 503. A proven empty bucket returns zero. Unknown valid administrator collections are empty; out-of-scope agent names return 403. No DNS, crawl, index write, Webgraph or ranking work occurs.

CLI: `scoutroctl index metrics [--collection NAME]` and `scoutroctl ask 'Wie viele Seiten?' [--collection NAME]` choose the existing admin/agent authentication path. OpenAPI, actions.json, registry and generated MCP names describe the same contracts. New grants are not added to presets.

## Real MCP over stdio

Run `tools/scoutro/scoutro-mcp` with Python 3. Set `SCOUTRO_URL` to the intended Scoutro HTTPS origin (literal loopback HTTP is allowed for local tests), and `SCOUTRO_TOKEN_FILE` to a protected agent-token file, or use `SCOUTRO_TOKEN`. Do not provide administrator passwords. A typical MCP client config uses the absolute script path as `command` and these values in its process environment. No HTTP listener, global admin account, installation, crawl or deployment is required.

The adapter supports MCP `initialize`, notifications, `ping`, `tools/list` and `tools/call` with newline-delimited JSON-RPC over stdin/stdout. It negotiates 2024-11-05, 2025-03-26, 2025-06-18 and 2025-11-25. Only catalogued, non-mutating GET actions allowed by fresh agent capabilities are exposed. `system.questions` is available when at least one delegate is granted; each selected action may still return a clear denial. SEO tools use the shared `seo.read` grant. Explicit global read grants remain visibly global in their tool descriptions; the adapter never adds grants. Write/crawl-start/config-set mappings remain descriptive mappings, not runnable tools.

Every list/call refreshes capabilities and each action is independently authorized at the agent API, so revocation, grants, ownership, rate limits and scopes remain authoritative. Paths and schemas come from the local generated catalog; clients cannot supply arbitrary paths, URLs, raw queries or headers. Redirects are refused so the token stays on the configured origin. HTTPS uses the standard trusted CA store; HTTP is restricted to literal loopback. Proxy environment variables are deliberately ignored for this credential-bearing adapter. HTTP timeout is 15 seconds; input and response bounds are 1 MiB. Stdout carries JSON-RPC only; errors do not print tokens or configuration secrets.

The existing public `/mcp` search servlet is separate and unchanged. Its legacy search tool does not represent the Scoutro Actions authorization boundary. `mcpTool` entries in actions.json remain names/mappings; only eligible tools returned by this adapter's `tools/list` are implemented here. There is no Streamable HTTP transport, write-tool support or all-admin MCP server in this PR.

## Validation and limits

Focused Java aggregate/router/grant/audit tests, real temporary Solr, authenticated API and JSON/SSE chat checks, live MCP-to-agent calls, offline protocol/schema/revocation/redirect/size tests, Search/SEO/Citation/Discovery/robots-security regression suites, locale checks and mobile browser tests use only disposable DATA/fakes. Model configuration is unnecessary for successful system replies. DNS-rebinding analysis and transport plan: [DNS rebinding](DNS_REBINDING_ANALYSIS.md).

Large local aggregates can return 503 at the two-second query budget. Production-size performance and interoperability with third-party MCP clients were not tested; stdio protocol and a real local Scoutro API were tested. Deterministic text classification has the documented vocabulary boundary; future intent expansion must keep unsupported system requests out of content search.

Verified targets: `ant scoutro-agents-test scoutro-dashboard-test locale-refresh-test citation-postprocessing-test robots-redirect-security-test jetty12-server-test`; final agent batch 173 cases; 11 CLI/description contracts; 8 MCP protocol/boundary cases; live SEO/flow/system API and JSON/SSE/MCP calls; 590 LLM, 192 Dashboard, 282 SEO, 71 system chat and 123 existing flow UI checks. Chat, LLM, Dashboard and SEO include 360/390/412/768/1280. Locale guard: nine pages × 14 locales, zero collisions. OpenAPI 3.1 validation passes. The 137 existing Discovery cases have 12 optional runtime/state-copy skips; the additional fake DNS-rebinding reproduction passes separately. No production-size or third-party MCP-client test was performed.
