# Collection-crossing customer and partner suggestions (package A)

Base checked: `main` at `7847fe1ed54eda64348eaa64cd15d7eb8c107639`
(Scoutro 0.8.7). The existing `DerivedService` already writes customer and
partner suggestions with different `coll_a` / `coll_b`; this package changes
their read projection, API and presentation only.

## Scope and read contract

- `KnowledgeApi` supplies the administrator's authenticated unrestricted grant
  separately from the collection filter. `ScopedActions` supplies the agent's
  fixed grant separately from its validated filter. `KgReader.within` intersects
  them; no client-controlled parameter adds permissions.
- `Suggestions` reads existing kinds 3/4 only. Both collection contributions
  must be permitted; the origin's side must match the view filter. Each endpoint
  must still belong to its contribution collection. Grouping precedes counting
  and paging: canonical counterpart and relationship, with customer direction
  retained and partners symmetric. Hidden contributions cannot affect totals,
  membership tags or the maximum sorting score.
- `BusinessView` keeps normal facts, sources and weak/structural derivations in
  the original view. Its `suggestions` field embeds the first 100 groups with
  total/next offset; legacy audience/match arrays expose that same first page.
  `/entities/{id}/suggestions` serves subsequent bounded pages (1–100).
- `BusinessGraph` extends only the center's requested suggestions to other
  permitted collections. Foreign nodes do not cause foreign ordinary facts to
  enter depth 2. Neighbor IDs are grouped with sets before paging. Canonical
  suggestion edge keys prevent reverse-traversal duplicates. Detailed supporting
  statements are expanded for displayed groups only.
- Every contribution retains its authorized collection pair, reason and date.
  Supporting statements are checked in their actual contribution collection,
  including both endpoints. Raw basis JSON is not forwarded. Missing/invisible
  references are omitted; accessible statement redirects are resolved and
  deduplicated. Incomplete support replaces the original reason with
  an explicit notice. Original extraction and stored derivations are unchanged.
- Target refs contain only permitted memberships, external tags and an explicit
  `target_collection`. Evidence/source links carry their own collection.
  Explicit contexts win over the global UI filter; browser Back restores the
  origin. Suggestions remain derivations and sorting scores are not probabilities.

API details: [API.md](API.md#knowledge-graph). Page usage and export semantics:
[ScoutroKnowledge_p.md](../help/ScoutroKnowledge_p.md). OpenAPI and the agent/MCP
catalog are generated by `tools/scoutro/generate_api_description.py`.

## Existing data and bounds

No schema migration, re-extraction, crawl, LLM call, derivation rebuild or
configuration change is needed. Existing rows become visible under the new
projection. Normal collection exports/downloads, change feeds, facets and
ordinary derived-list routes retain their strict collection scope; the separate
`kg.export` grant remains required. Network JSON/GraphML contain the loaded,
visible graph and its scoped suggestion contributions.

The current derivation computation caps still determine which rows exist; this
package neither produces missing matches nor changes matching rules. Suggestion
groups no longer disappear behind the old business/raw-derived display caps:
counts cover all authorized groups, and subsequent pages are available. Graph
requests keep their 200-node maximum and existing ordinary fact/weak-link limits
(2,000 facts per direction, 200 weak/structural rows). Depth-2 truncation does
not invent another direct-neighbor page. Read leases still impose their existing
time limit. Production-sized load measurements and a production-data review were
not performed.

## Validation

Run with JDK 17, Ant and resolved repository dependencies:

```sh
ant scoutro-kg-suggestions-test
ant all
node test/scoutro-ui/knowledge-suggestions-ui-test.mjs
python3 -m unittest discover -s test/scoutro-api -p test_mcp_adapter.py
python3 test/scoutro-ui/check-locale-identifiers.py ScoutroKnowledge_p.html
node --check htroot/env/scoutro/knowledge.js
git diff --check
```

The focused Java target covers same/cross-collection suggestions, admin and
agent authorization, inaccessible candidates and evidence, origin-only facts,
strict exports and grant separation, multi-membership grouping, customer
direction, symmetric partners, depth-2 deduplication and 205-row pagination
beyond the former business/graph caps. The browser suite uses real page/JS/CSS
with a simulated read API (EN/DE, 1280/390 pixels): checkboxes, external tags,
target and Back navigation, scoped evidence and source links, evidence/group
pagination, JSON/GraphML exports and no horizontal overflow. It starts no peer,
crawl or LLM.

Observed validation: 107 focused Java tests, `ant all` (60 further tests),
44 browser checks, 9 MCP tests, locale/JS/whitespace checks and OpenAPI 3.1
validation with `openapi-spec-validator` 0.7.2 passed. The direct
`EmbeddedSolrConnectorTest` also passed (4 tests).

Additional repository check limitation: `test/jetty-solr-dependency-guard.sh`
fails on `lib/solr9-bridge-jetty-alpn-java-client-10.0.26.jar`:
`unrelocated Jetty reference`. The retained names occur in manifest/NOTICE,
Maven metadata and `module-info.class`. The guard and relocation source are
byte-identical to the base commit; bridge generation/dependencies were not
changed. `test/solr9-jetty-bridge-spike.sh` therefore stops at that guard before
running its connector tests. Those four tests were run directly and passed;
the guard failure remains unresolved in this package.

The full live-peer UI/E2E suites that crawl fixtures were not run. No release,
merge, production operation or Olares deployment was performed. Later packages
for extraction, job/system signals, retention and new domain matching are out
of scope.
